# 开发与验收流程

更新：2026-11-15。配合 [Roadmap](../ROADMAP.md) 使用。本文规范后续开发，不表示任何功能已完成。

## 1. 每次开发从同一个入口开始

1. 阅读 `ROADMAP.md`、对应产品约束、当前里程碑计划和交接记录。
2. 检查分支、工作区改动和实际源码；用户未提交的内容保留。
3. 明确这次只交付哪个可验收结果、依赖什么、结束条件是什么。
4. 把任务、证据链接和阻塞原因记录在实施计划；未完成的勾选项不能凭印象勾选。

旧计划是历史上下文，不因为存在未勾选项就自动恢复执行。当前范围以新 Roadmap 及获准任务为准。

## 2. 开始实施前的准入条件

- [ ] 有可观察的用户结果，关联一个里程碑退出条件。
- [ ] 有源码依据，区分“缺实现”和“已有但未验收”。
- [ ] 有明确文件、服务接口、数据兼容方式和失败语义。
- [ ] 有相关验证场景；涉及付费/恢复/数据迁移的任务先定义失败案例。
- [ ] 有部署和数据回退方案；版本控制回退不等于数据库回退。
- [ ] 依赖已经交付或任务中明确包含，不写“等后面再接上”却宣称完成。

大任务先拆成可独立验收的交付单元，通常每个单元包含实现、测试和文档，而非分别做“所有后端”“所有前端”“最后补测试”。

## 3. 推荐开发循环

1. **定义行为**：写出成功路径和关键失败路径。
2. **验证缺口**：对业务逻辑变化先运行目标测试，确认当前行为为何不满足。
3. **最小实现**：复用现有核心，避免在 CLI、API 和前端各复制一套状态/费用逻辑。
4. **定向验证**：运行与变更相关的测试；低影响文档改动只需检查路径、链接和一致性。
5. **集成检查**：在里程碑门槛处运行相关完整套件、构建和 E2E；没有新变更不反复跑同一套检查。
6. **评审**：检查需求覆盖、重复付费风险、兼容性、输入边界和证据是否足够。
7. **交付记录**：更新计划勾选、能力矩阵、未解决问题和交接信息；按任务形成小提交。

一个任务可以代码完成但真实验收阻塞。两种状态必须分开，不用“测试通过”代替“产品交付”。

## 4. 测试分层

| 层 | 证明什么 | 不能证明什么 |
|---|---|---|
| 单元/契约 | 状态迁移、金额计算、能力匹配、失效规则 | 网络现实与最终画面质量 |
| 本地集成 | SQLite、真实 FFmpeg、文件与迁移行为 | 供应商协议当前可用 |
| Mock 媒体 E2E | 项目到导出完整路径，零外部 API | 真实模型/TTS 的效果和账单 |
| 浏览器 E2E | 用户实际操作、断线/刷新、进度与产物 | 模型视觉质量 |
| 故障注入 | 重启、重复、超时、429、下载失败与恢复 | 全部供应商真实故障组合 |
| 真实 E2E | 当前账号、协议、计价和作品观感 | 未来供应商行为保证 |

当前常用命令（在对应目录执行）：

```bash
# ai-video-studio/
uv run --extra dev --extra web pytest -q
# vbench/
uv run --extra test pytest -q
# ai-video-studio/web/
node --test src/guidedHelpers.test.js
npm run build
```

新 E2E 的命令必须随实现加入计划和文档，未创建的命令不能描述成现有能力。

## 5. 必测故障矩阵

M0 先记录现状；M1 实现可靠性测试，M3 通过浏览器与自动编排重新验证关键路径。

| 注入点 | 预期结果 |
|---|---|
| 提交前进程退出 | 无远程副作用，恢复后可认领 |
| 远程接受但响应丢失 | 保留预留、进入未知状态、不自动重复 POST |
| remote ID 已落库后退出 | 恢复查询该 ID |
| 重复 HTTP 请求/双击 | 相同请求返回原任务，不创建第二个计费尝试 |
| 两个 Worker/租约接管 | 一个逻辑尝试，未知副作用先对账 |
| 403 | 配置/权限阻塞，不无限重试 |
| 429 | 可证实未受理时按 Retry-After/退避；不确定受理则按未知处理 |
| 下载中断 | 临时文件隔离，恢复下载不重生成 |
| 文件损坏/时长不合格 | 本地可修复则修复；否则有限、有额度的重试 |
| API/Worker/渲染器重启 | 任务状态及输出可追踪，旧产物不覆盖 |
| 并发预算预留 | 原子拒绝超额新任务，估算与账单差异另记 |
| 镜头/字幕在渲染中修改 | 旧任务使用固定快照，新编辑属于新版本 |
| 磁盘满/素材丢失 | 清晰失败，保存源素材及任务记录，不显示完成 |

## 6. 真实模型验收协议

1. 使用独立验收项目；记录源码 commit 和工作区是否有改动。
2. 检查当前模型能力、账号权限、计价来源及已有未决请求。
3. 展示本次步骤、预计费用和最大本地授权额度；得到明确付费授权后执行。
4. 先 20–30 秒，再 60 秒；M5 才升级到 180/300 秒。
5. 保留每个请求的关联 ID、素材哈希、输出、各阶段耗时与费用状态。
6. 人工完整观看视频，记录叙事、人物、音画、字幕问题以及实际干预次数。

验收不能通过隐藏失败镜头、改变目标时长或把人工剪辑计为自动生成来达成。供应商最终账单不可得时明确写“估算/待对账”。

## 7. 证据包与完成标准

媒体、真实报告和数据库保存在独立的 `STUDIO_HOME` 或批准的本地验收目录，不提交到源码仓库。仓库可提交不含敏感数据的总结和报告 schema。

每份证据包至少包含：

- 源码 commit、dirty 状态、Python/Node/FFmpeg 版本和运行配置；
- 项目、运行、任务、尝试的关联 ID；
- Storyboard、Timeline、RenderSnapshot 版本；
- MP4、字幕和素材哈希；
- 技术探测结果、质量问题和人工观看结论；
- 费用的预留/估算/实际/未知状态；
- 自动化通过项、人工参与步骤、阻塞及未验证项；
- 使用的命令、退出码和证据文件位置。

任务完成需：目标行为通过、关键失败路径通过、兼容性已验证、文档更新、无隐瞒的阻塞。

里程碑完成还需：Roadmap 的全部退出条件有证据，注明本地/Mock/真实/人工的覆盖范围，并由项目负责人或用户确认验收。技术人员可提交验收结论，不自行修改标准。

## 8. 变更与回退

范围变更记录最少写：

```text
所属里程碑：
问题及证据：
拟改变的用户结果：
新增/推迟的范围：
费用、数据及时间影响：
新验收条件：
决定人及日期：
```

涉及数据库时备份数据库与引用媒体，验证备份可读取；迁移采用版本号和幂等策略。不得用删除旧项目作为迁移方案。

产品方向改变需更新产品约束和 Roadmap；单项技术调整只更新对应计划与理由。默认不升级整个技术栈、不顺带重写其他工作流。

## 9. 每个里程碑的回顾

比较基线：从输入到初稿耗时、必须点击次数、生成尝试次数、恢复成功情况、费用估算偏差、局部精修新增成本。

没有测量的指标写 `not_measured`，不填 0。先记录基线再收紧性能目标，不能只报功能数量。
